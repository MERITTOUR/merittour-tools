# 리조트 마스터의 「기간별 보유 예외」

> 상태: **구현 완료** · 대상: `tools/dashboard/index.html` · 순수 로직은 `shared/util.js`
>
> 목적: 숙소·룸타입의 보유 객실 수가 날짜에 따라 다를 수 있게 한다.
> 편집은 **① 리조트 마스터에서만** 한다(호텔 블록 표에서 편집하지 않는다).

---

## 1. 지금 구조와 한계

보유값의 단일 출처는 리조트 마스터의 `rooms`다.

```js
{ key:'ganji', name:'간지호텔', rooms:{'트윈':15}, ... }
```

`deriveBlkMaster()`가 이걸 `blkMaster["간지호텔|트윈"] = 15` 로 펼치고, 아래 두 함수가 모든 소비처에 값을 공급한다.

| 함수 | 반환 | 쓰는 곳 |
|---|---|---|
| `blkBlockOf(hotel, room)` | 룸타입 1개의 보유 | 블록 현황 표, 전기카트 표, 미분류 판정 |
| `blkPoolCap(pool)` | 풀(숙소 묶음) 보유 합 | 출발 일정 조회, 대기 전환 점검, 예약 가능 공지 PNG, 판매 시뮬, 요금달력 `vcalAvail` |
| `blkPoolCapByName(name)` | 숙소 정원 합 | 마스터 카드 헤더 정원 배지 |

**한계: 세 함수 모두 날짜 인자가 없다.** 그래서 8월만 트윈 20으로 늘리거나 9/14 하루만 9로 줄이는 것을 표현할 방법이 없다. 현재 날짜별로 달라질 수 있는 유일한 값은 호텔 블록 탭의 **오버부킹 보정(`blkOver`)** 뿐인데, 이건 내 PC의 localStorage에만 있고 마스터 내보내기에 포함되지 않아 직원 간 공유가 안 된다.

## 2. 제안 — 숙소마다 「기간 예외」 목록을 둔다

리조트 객체에 배열 하나를 추가한다. 기존 `rooms`(기본 보유)는 그대로 두고, 예외만 얹는 방식이다.

```js
{
  key:'ganji', name:'간지호텔',
  rooms:{'트윈':15},                       // 기본 보유 — 예외가 없는 모든 날
  roomExceptions:[                          // 신규
    { id:'x1', room:'트윈', from:'2026-08-01', to:'2026-08-31', qty:20, memo:'성수기 증실' },
    { id:'x2', room:'트윈', from:'2026-09-14', to:'2026-09-14', qty:9,  memo:'객실 보수' }
  ]
}
```

**입력 단위는 기간(시작일~종료일) 하나로 통일한다.** 월 단위도, 하루도, 주 단위도 같은 줄로 표현된다(하루짜리는 시작=종료). 월 전용 입력칸을 따로 두는 것보다 개념이 하나뿐이라 배우기 쉽고, "9/14 하루만" 같은 실제 요구를 오버부킹 보정에 떠넘기지 않아도 된다.

### 겹칠 때의 우선순위

**기간이 짧은 예외가 이긴다.** 길이가 같으면 나중에 등록한 것이 이긴다.

위 예시에서 9/14는 x1(31일)과 x2(1일)에 모두 걸리지만 x2가 짧으므로 **9실**이 적용된다. "8월은 20으로, 단 9/14만 9로"라는 사람의 말 순서와 결과가 같다. 등록 순서에 결과가 좌우되지 않는다는 점이 중요하다.

길이가 같은 예외가 겹치면 마스터 화면에 경고 배지를 띄운다(무시하고 저장은 되되, 어느 쪽이 적용 중인지 표시).

### 그날의 최종 보유

```
최종 보유(숙소, 룸타입, 날짜)
  = 기간 예외에 걸리면 그 예외의 qty, 아니면 rooms[룸타입]     ← 마스터 (공식값, 전 직원 배포)
  + 오버부킹 보정 blkOver[숙소|룸타입|일]                      ← 내 PC 임시 시뮬레이션
```

두 축의 역할이 다르므로 **둘 다 유지**한다.

- **마스터 기간 예외** — 실제로 확보한 객실 수의 변경. 관리자가 입력하고 「마스터 내보내기」로 배포하면 전 직원이 같은 값을 본다.
- **오버부킹 보정** — "이 날만 2개 더 팔면 어떻게 되나" 같은 개인 시뮬레이션. 공유되지 않고 언제든 초기화 가능.

화면에 이 구분을 문구로 명시한다(현재는 오버부킹만 있어 혼동될 여지가 없었지만, 둘이 공존하면 반드시 필요하다).

## 3. 함수 변경 — 여기가 작업의 본체

날짜를 모르는 함수 3개에 날짜를 흘려보내야 한다. **호출부가 문제다.** 여러 소비처가 "정원을 한 번 구해놓고 날짜를 반복"하는 구조라서, 반복 안으로 조회를 옮겨야 한다.

### 3-1. 새 조회 함수

```js
MT.roomCapOn(baseRooms, exceptions, room, ymd)  // 기본 보유 + 기간 예외 해소 → {qty, exc} | null
blkBlockOn(hotel, room, ymd)      // 기존 blkBlockOf의 날짜 인자판
blkPoolCapOn(pool, ymd)           // 기존 blkPoolCap의 날짜 인자판
blkPoolCapBase(pool)              // 예외 무시한 기본 합 — "측정 가능한 풀인가" 판정 전용
```

기존 `blkBlockOf` / `blkPoolCap`은 **지우지 않고** 기본값 조회로 남긴다. 날짜를 모르는 자리(마스터 카드 헤더 정원 배지 등)가 계속 쓴다.

`cap == null`(정원 미등록) 판정은 날짜와 무관하므로 `blkPoolCapBase`로 분리한다. 그러지 않으면 "예외 때문에 그날만 0"인 경우와 "애초에 정원 미등록"인 경우가 뒤섞인다.

### 3-2. 고쳐야 할 호출부

| 위치 | 지금 | 바꿀 내용 | 위험도 |
|---|---|---|---|
| 블록 현황 표 `blkRenderStatus` | 행마다 `blk` 한 번 | 칸마다 `blkBlockOn(…, 날짜)` | 낮음 — 이미 칸 단위로 도는 구조 |
| 전기카트 `blkRenderCart` | 행마다 `cap` 한 번 | 칸마다 조회 | 낮음 |
| 출발 일정 조회 `blkRenderDepart` | `cap` 한 번 → 연박 구간 최소 잔여 | 연박 루프 안에서 날짜별 cap | **높음** |
| 예약 가능 공지 `noticeDepartList` | 위와 동일 | 위와 동일 | **높음** — 손님 발송물 |
| 대기 전환 점검 `blkRenderWait` | `cap` 한 번 | 그 팀 출발일의 cap | 중간 |
| 판매 시뮬 `blkRenderSim` | `blk` 한 번 | 날짜별 cap | 중간 |
| 요금달력 `vcalAvail` | `cap` 한 번 → 월 경계 넘어 반복 | 날짜별 cap | **높음** — 월 경계 처리와 얽힘 |

**출발 일정 조회·공지 PNG·요금달력이 핵심 위험 구간이다.** 연박 구간의 최소 잔여를 구할 때 하루라도 보유가 다르면 결과가 달라진다. 여기를 빠뜨리면 표에는 정확한 보유가 보이는데 "출발 가능 일정"은 옛 정원으로 계산되는, **틀린 줄 모르고 손님에게 나가는** 상태가 된다.

그래서 표시(블록 현황)만 먼저 내보내고 나머지를 나중에 하는 분할 배포는 권하지 않는다. **한 번에 전부 반영해야 한다.**

## 4. 마스터 화면 UI

리조트 마스터 카드의 「호텔 블록 (1일 보유 객실)」 그룹 안, 기존 룸타입 입력 아래에 붙인다.

```
호텔 블록 (1일 보유 객실)
  트윈           [ 15 ] 객실          ← 기본 보유 (기존 그대로)
  [룸타입   ][보유] [+ 룸]

  기간 예외 (이 기간만 다른 보유)
   · 트윈  2026-08-01 ~ 08-31   20실   성수기 증실        [✕]
   · 트윈  2026-09-14 ~ 09-14    9실   객실 보수          [✕]
   [트윈 ▾] [시작일 📅] [종료일 📅] [수량] [메모        ] [하루] [+ 추가]
```

- 「하루」 버튼 = 종료일에 시작일 복사 (하루짜리 예외를 두 번 고르지 않게).
- 룸타입은 그 숙소에 등록된 것만 드롭다운으로 — 오타로 매칭이 깨지는 걸 막는다.
- 저장 시 검증: 종료일 ≥ 시작일, 수량 0 이상(0 = 그 기간 판매 불가로 유효), 룸타입 존재.
- 예외가 있는 숙소는 카드 헤더 정원 배지 옆에 「예외 N건」 표시.
- 추가·삭제·수정은 모두 **변경 이력**에 남긴다(`logChange`) — 기존 단가 변경과 같은 방식.

## 5. 블록 현황 표에서의 표시

칸 아래 줄(그날 보유)은 이미 들어가 있다. 여기에 출처 구분만 얹는다.

- 기간 예외가 적용된 날 → 보유 숫자에 밑줄 + 툴팁 "기간 예외 적용 (2026-08-01~08-31, 성수기 증실)"
- 오버부킹 보정이 얹힌 날 → 지금처럼 툴팁에 `20+2=22`

두 가지가 동시에 걸리면 툴팁에 둘 다 표기한다.

## 6. 저장·배포·호환성

- `roomExceptions`는 리조트 객체 안에 있으므로 **「마스터 내보내기/불러오기」에 자동으로 실려 나간다.** 별도 작업 불필요.
- `loadResortMaster()`의 병합(`{...def, ...s}`)에서 기존 저장본에 이 필드가 없으면 그냥 빈 배열이 된다 → **현재 동작과 100% 동일.** 마이그레이션 코드가 필요 없다.
- 기본값은 `RESORT_DEFAULTS`에 넣지 않고 `loadResortMaster()`·불러오기·초기화 경로에서 정규화한다(`if(!Array.isArray(r.roomExceptions)) r.roomExceptions=[]`). 숙소 18개에 같은 줄을 반복하지 않아도 되고, 구버전 마스터 파일도 같은 경로로 처리된다.
- 오버부킹(`blkOver`)은 지금처럼 내보내기에서 제외한다(개인 시뮬레이션이므로).

## 8. 확정된 결정

1. **입력 단위** — 기간(시작~종료) 하나로 통일. 하루짜리는 「하루」 버튼으로 종료일을 시작일에 맞춘다.
2. **오버부킹 보정 존치** — 마스터 예외와 병존. 화면 세 곳(마스터 힌트·설정 탭·판매 시뮬 안내)에 역할 차이를 명시했다.
3. **겹침 우선순위** — 짧은 기간이 우선, 동률이면 나중 등록. 동률 겹침은 마스터 카드에 ⚠ 경고를 띄운다.

## 9. 구현 결과

**순수 로직** (`shared/util.js` · `tests/util.test.mjs` 8개 케이스)
`roomExcValid` · `roomExcSpan` · `pickRoomException` · `roomCapOn` · `roomExcConflicts`

**조회 함수** (dashboard)
`blkBlockOnInfo(hotel,room,ymd)` → `{qty, exc}` · `blkBlockOn` · `blkYmd(day)` ·
`blkPoolCapOn(pool,ymd)` · `blkPoolCapBase(pool)` (정원 등록 여부 판정 전용)

기존 `blkBlockOf` · `blkPoolCap`은 기본값 조회로 존치 — 날짜를 모르는 자리(마스터 정원 배지 등)가 계속 쓴다.

**전환한 소비처 8곳**
블록 현황 매트릭스(요약 집계·선택 합계 행·각 행 셀) · 엑셀/PNG 내보내기 매트릭스 ·
출발 일정 조회(연박 최소 잔여 + 일자별 잔여 표) · 예약 가능 공지 PNG ·
대기 전환 점검(출발일 정원) · 판매 시뮬(오버부킹 기준선) · 요금달력 `vcalAvail`(월 경계 포함)

전기카트 표는 리조트 마스터에 없어 예외가 적용될 수 없으므로 그대로 두었다.

**결정한 세부 규칙**
- 룸타입이 마스터에 없으면 남아 있는 예외도 무시한다(`blkBlockOnInfo`가 null 반환). 정원 합산과 칸 표시가 어긋나지 않게 하기 위함.
- 룸타입을 삭제하면 그 룸타입의 예외도 함께 정리하고 변경 이력에 남긴다(고아 예외 방지).
- 수량 0은 유효한 입력이다(그 기간 판매 불가). 다만 미입력(`''`)은 거부한다 — `Number(null)===0`이라 명시적으로 걸러야 했다.

**검증**
- `npm run verify` — 문법 20파일/21스크립트 + 단위 테스트 17개 통과
- Chromium 실브라우저 시나리오 73개 통과 (페이지 에러 0)
  - 조회: 경계일 포함, 짧은 기간 우선, 등록 순서 무관, 기간 밖 복귀
  - 블록 표 / 출발 일정 조회 / 공지 PNG / 요금달력이 **같은 값**(8/13 3박 = 잔여 1)을 쓰는지 대조
  - 오버부킹과 합산(예외 9 + 오버 2 = 11), 웹오픈 기준선이 그날 보유인지
  - 마스터 UI: 검증 거부 3종·추가·삭제·겹침 경고·변경 이력·헤더 배지
  - 내보내기/불러오기 왕복 복원, 구버전 파일(예외 필드 없음) = 기존 동작
  - 예외를 모두 지우면 변경 전 값으로 복귀(회귀 안전망)

**부수 변경**
dashboard가 `shared/util.js`를 로드하도록 `<head>`에 추가했다(기존에는 안 불렀다).
