# 프로젝트 셋업 가이드 & 향후 진행 방향

사이님(Min)이 두 운영 관리 시스템을 프로젝트로 옮겨 진행하기 위한 종합 안내서.

> **저장소는 3개, 프로젝트는 2개로 나눈다.**
> - MERITTOUR 프로젝트 ← `merittour-tools`(사내 도구함, 주력) + `merittour.github.io`(고객 안내 페이지, 설계 참고용)
> - SaiZen 프로젝트 ← `saizenjp.github.io`(현장 운영 자동화 앱)
>
> 메리트투어 쪽 저장소 2개를 한 프로젝트에 묶는 이유는, 둘 다 한국 본사의 업무이고(도구함=직원용, 고객페이지=고객 안내용) 같은 데이터·표준을 공유하기 때문이다. 사이젠은 일본 현장·일본어·현장 산출물이라 성격이 달라 분리한다.

## 1부. 프로젝트 만들고 셋업하기

### 1단계 — 프로젝트 2개 생성
Claude 좌측 사이드바에서 "프로젝트" → "새 프로젝트"로 두 개를 만든다.
- **MERITTOUR 운영 관리 시스템**
- **SaiZen 운영 관리 시스템**

### 2단계 — 각 프로젝트에 지침(커스텀 인스트럭션) 넣기
프로젝트 설정의 "지침(Instructions)" 칸에 아래 문서 내용을 붙여넣는다.
- MERITTOUR 프로젝트 ← `메리트투어_프로젝트_지침.md` 내용
- SaiZen 프로젝트 ← `사이젠_프로젝트_지침.md` 내용

### 3단계 — 각 프로젝트에 지식(파일) 올리기
프로젝트의 "지식(Project knowledge)" 영역에 다음을 업로드한다.

**MERITTOUR 프로젝트 지식:**
- `merittour-tools-main.zip` (사내 도구함 저장소 전체 — dashboard 포함 최신본)
- `merittour.github.io-main.zip` (고객 안내 페이지 저장소 — index·about·14hills·yamanami. confirm/ 폴더는 아직 미생성)
- `dashboard_tech_spec.md` (현재 dashboard 구조 설명)
- 엠클릭 샘플: 예약리스트, 일행별예약 (2종 통합 완료 — 일행별예약에 항공·PNR·여권·시각 흡수, 구 APIS·현지도착 폐지)
- 호텔 블록 샘플 2종: 호텔블록및요금조회.xlsx, 월별호텔수배현황.xls
- 알리고 PNR 안내 템플릿 xlsx
- merit-logo.svg (로고)

> ZIP 업로드 시 파일명은 영문으로(한글 파일명 다운로드 실패 이슈와 동일 환경).

**SaiZen 프로젝트 지식:**
- `saizenjp.github.io-main.zip` (사이젠 저장소 전체 — app/index.html + assets 로고 포함)
- 또는 개별로: `saizen-app-latest.html`(자동화 앱 본체) + 로고 3종(logo-saizen-*.svg)
- 엠클릭 샘플 4종: 예약리스트, 일행별예약, 현지도착, 그룹코드 참조테이블

> 팁: 저장소는 zip 통째로 올리는 게 가장 확실하다. GitHub의 Code → Download ZIP으로 받아 올리면 Claude가 전체 구조를 본다. (Claude는 public 저장소라도 raw/API 주소를 임의로 직접 호출하지는 못하므로, zip 업로드가 가장 안정적이다.)

### 4단계 — 작업 이어가기
프로젝트 안에서 새 대화를 시작하면 지침과 지식이 자동 적용된다. 첫 대화에서 "dashboard 이어서 작업하자" 또는 "사이젠 v14 작업하자"처럼 시작하면 된다.

> 참고: 지금까지의 채팅 메모리는 프로젝트 밖에 쌓여 있어 프로젝트 대화에서 곧바로 끌어 쓰진 못한다. 하지만 위 지침·지식 문서에 핵심 맥락을 다 담았으므로 작업에 지장은 없다. 과거 대화 내용이 필요하면 "예전에 ~했던 것 찾아줘"라고 하면 검색할 수 있다.

## 2-1부. 장기 전략 — 콜드 스탠바이(엠클릭 대체 대비)

> 2026.06 논의 확정. 당장 착수 아님. **앞으로의 모든 작업이 이 방향과 어긋나지 않게 하는 것**이 목적이며, 실제 토대 구현은 별도 시점에 시작한다.

### 목표 한 줄
**평소엔 보완, 유사시엔 대체.** 엠클릭을 이기는 것이 아니라, 엠클릭이 사라져도(장애·계약 종료) 업무가 멈추지 않도록 며칠 안에 전환 가능한 백업 운영 레이어를 갖춘다. 시나리오는 일시 장애가 아니라 **계약 종료(영구 중단)까지** 본다.

### 핵심 구조 (단방향, 충돌 없음)
```
[평소 모드 — 엠클릭이 원본]
  엠클릭 → 엑셀 → 대시보드(정리·요금검증·안내) → Supabase에 적재(거울)
                                                    ↑ 손님 확약 응답도 여기로 되돌아옴

[유사시 모드 — 엠클릭 중단 시 Supabase가 본체로 승격]
  엠클릭 中 → Supabase 원본(어제까지 전부 보존) → 대시보드 직접 입력 모드(폼으로 신규 예약)
```
- 평소엔 **엠클릭이 원본, Supabase는 read-only 거울**. 양방향 동기화의 충돌(둘 중 뭐가 맞나)을 피하기 위해 단방향으로 둔다.
- 유사시에만 Supabase를 원본으로 **승격**하고, 신규 입력은 대시보드 폼으로 이어간다.

### 결정적 토대 (이게 척추)
> **엑셀을 업로드할 때마다 그 예약 데이터를 Supabase에 적재한다.**

현재는 업로드 데이터가 브라우저 메모리에만 살고 새로고침하면 사라진다. 이걸 Supabase 영구 저장으로 바꾸면, 평소엔 "조회 편의"지만 유사시엔 "유일한 원본"이 된다. 화려한 기능이 아니라 이 **조용한 적재 습관**이 대체 시스템의 본질이다.

### 그 위에 얹히는 것 — 손님 확약 응답 (양방향)
- 확약서(`confirm/{행사번호}.html`)에 **[진행 확인] / [진행 보류]** 버튼 → Supabase에 기록 → 직원 대시보드에서 누가/언제/무엇을 눌렀는지 조회.
- 데이터가 처음으로 우리 쪽으로 **되돌아오는** 지점. 적재 토대 위에 자연스럽게 얹힌다.
- **신원 식별 = 링크 고유토큰 방식**(로그인 불필요, 50~70대 고객 적합). 무작위 토큰 ↔ 손님 매핑을 Supabase에 미리 저장, URL은 `?t={토큰}`만. 이름·전화번호 URL 노출 없음.
- **받는 단위 = 대표자/개인 둘 다 지원.** 대표자 1개(행사당) 또는 탑승객별 토큰 발급. eventSeq로 묶고 행사번호는 표시용.
- 테이블 2개: `confirm_token`(토큰↔손님 매핑, 대시보드가 INSERT) + `confirm_response`(손님 클릭 기록). 번복 허용(새 row INSERT, 최신만 유효), 중복 클릭 무시, 보류 사유 선택 입력, 출발일 지난 토큰 비활성.

### 선결 과제 (양쪽 모드 공통)
**RLS 보안 정리.** 손님이 직접 쓰는 데이터와 사내 원본이 같은 Supabase에 쌓이므로, 현재 always-true 쓰기 정책을 반드시 잠가야 한다. `confirm_token`은 anon SELECT만, `confirm_response`는 유효 토큰일 때 anon INSERT만, 조회·통계는 직원 권한으로. (5부 로드맵 "Supabase 적용"의 RLS 작업과 동일 선상.)

### 직접 만들기의 경계선
"직접 한다"가 곧 "엠클릭 통째로 대체"는 아니다. **업무 흐름(예약·고객 응대·확약·안내)은 직접 가져오되, 규제·정산·장부의 코어(회계 정산·세금계산서·법적 장부 보관)는 외부 도구에 남긴다.** 후자는 여행업 규제·세무와 얽혀 직접 구현 시 전문가 자문 필요 영역.

### 착수 순서 (정해지면)
1. **(토대)** Supabase 적재 파이프라인 + RLS 잠그기 — 안 보이지만 대체제의 척추. *먼저.*
2. **(기능)** 손님 확약 응답 버튼 + 응답 현황 조회 — 토대 위에 얹기.
3. **(대체 모드)** 엠클릭 없이 신규 예약 직접 입력 폼 — 비상시 켜는 모드.

### 사이젠 이식 메모 (2026.06 — 착수 시 이걸 보면 사이젠 재분석 불필요)

> 사이젠(`Saizen-hub`)이 동일 패턴을 이미 구현·검증해둠. 메리트투어(`Merittour-hub`, AWS ap-northeast-2 서울, 무료 티어)는 **설계가 아니라 이식**이다. 참고 파일: `saizenjp.github.io/ops/hub/step1.html` + `ops/hub/sql/01_schema.sql`·`04_rls_anon.sql`. 두 조직은 **별개 Supabase 프로젝트**(키·RLS 독립).

**사이젠 연동 방식 (그대로 가져옴)**
- supabase-js를 CDN 로드(`cdn.jsdelivr.net/npm/@supabase/supabase-js@2`).
- URL·anon key를 **사용자 입력 → localStorage 저장**(코드 하드코딩 아님 → public 저장소 안전). 키 입력란에 "공개돼도 안전한 키" 안내.
- `connect()`: `createClient(url,key)` 후 `bookings`에 `select(head:true, count:exact)`로 가벼운 연결 확인.
- `upsertChunked(table, rows, conflict)`: 500행씩 잘라 `onConflict` 키 기준 upsert → **같은 파일 재업로드해도 중복 없이 덮어쓰기**(화면의 "중복되지 않으니 안심하세요"가 이것).

**사이젠 스키마 = 2층 구조** (엠클릭 원본층 → 현장 운영층). 메리트투어는 **원본층만** 떼어온다.

| 사이젠 테이블 | 메리트투어 | 비고 |
|---|---|---|
| `bookings` | **가져옴** | 예약리스트. event_seq PK = onConflict 키. |
| `passengers` | **가져옴** | 일행별예약(항공시각 4종·PNR·항공사·편명·사전좌석·여권 포함, 2종 통합). onConflict=`id`. |
| `member_codes` | 제외 | 그룹코드는 사이젠 전용. |
| `guests`~`transactions` | 제외 | 현장 운영층(룸·라운딩·식사·거래). 메리트투어 무관. |

**메리트투어 고유 추가** (사이젠에 없음): `confirm_token`(토큰↔손님 매핑), `confirm_response`(손님 클릭 기록). 손님 확약 응답 수신용.

**연동 코드 조정 2가지뿐**: ① localStorage 키 `saizen_sb_*` → `mt_sb_*`. ② 적재 시점 = 메리트투어 `analyze()` 끝에 연결(사이젠은 `run()`에서 실행). `teams` → bookings/passengers row 변환 후 upsert.

**RLS — 여기만 사이젠과 다르게 (중요)**
사이젠 RLS는 전 테이블 `to anon, authenticated using(true) with check(true)` = anon 읽기·쓰기 전면 개방(주석: "단일 운영팀 1단계"). 현장 직원 전용 내부 도구라 용인됨. **메리트투어는 손님이 직접 쓰는 `confirm_response`가 있으므로 그대로 따르면 안 됨.**
- `bookings`·`passengers`(사내 적재): 사이젠처럼 시작 무방하나 가능하면 게이트.
- `confirm_token`: anon **SELECT만**(자기 토큰 1건).
- `confirm_response`: anon **INSERT만**(유효 토큰 시). SELECT·UPDATE 차단.
- 이것이 로드맵·메모리에 반복 플래그된 "RLS 잠그기"의 실체. 사이젠 패턴 가져오되 **손님 테이블만 좁게 잠그기**가 핵심 차이.

## 4부. 두 시스템의 관계 (중요)

메리트투어(한국 본사)가 한국 고객 예약을 받아 → 사이젠(일본 현장)으로 보낸다. 따라서 두 시스템은 같은 엠클릭 데이터를 공유하되 쓰는 목적이 다르다.

| 구분 | MERITTOUR dashboard | SaiZen 자동화 앱 |
|---|---|---|
| 위치 | 한국 본사 | 일본 현장 |
| 언어 | 한국어 (고객) | 일본어 (현장) |
| 목적 | 예약 점검·고객 안내·발송 | 현장 운영 산출물 생성 |
| 입력 | 엠클릭 2종(예약리스트·일행별예약) | 엠클릭 3종 + 그룹코드 |
| 산출 | 화면 조회·알리고 양식·요금 검증 | 네임택·배정표·청구서 |

공유 표준(양쪽 프로젝트에 모두 반영): eventSeq 결합 키, 숙소 분류 규칙, 그룹코드 체계, 라운딩 용어, 라이트 모드.

## 5부. 작업 팁

- **코드가 문서보다 우선** — 프로젝트 지식 파일이 GitHub보다 뒤처질 수 있으므로, 차이 나면 업로드된 저장소 파일을 기준으로 한다.
- 결과물은 **ZIP만** 제공한다(회사 PC ZIP 업로드 가능, 개별 파일 동시 제공 불요).
- 다운로드 **파일명은 영문**으로 한다(한글 파일명은 사이님 환경에서 다운로드 실패). 파일 내부 제목·내용은 한글 유지.
- 새 기능은 항상 "설계 먼저 제안 → 확인 → 구현" 순서로 진행한다.
- 큰 변경 전에는 현재 저장소 zip을 지식에 다시 올려두면 Claude가 최신 상태를 정확히 안다.
- 도구가 늘어나면 sales 메인(`sales/index.html`)의 카드 목록도 함께 갱신한다.
- 색상·디자인·콘텐츠 표준은 지침에 다 정리되어 있으므로, 벗어난 요청이 아니면 자동 적용된다.
