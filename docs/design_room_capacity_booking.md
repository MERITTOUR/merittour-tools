# 룸타입 정원과 온라인 예약 인원 규칙

> 1단계(정원 데이터 + 대기 전환 환산): **구현 완료**
> 2단계(홈페이지 예약 연동): **설계 제안 — 확인 필요**
>
> 순수 로직은 `shared/util.js`, 마스터 UI는 `tools/dashboard/index.html`

---

## 1. 출발점 — "인원 = 객실 수"가 아니다

골프투어는 2인 1실이 기본이다. 그런데 마스터에는 **객실 수만** 있고 정원(1방에 몇 명)이 없었다.

```js
rooms: { '트윈': 15 }      // 15실이라는 것만 안다. 몇 명이 자는 방인지는 모른다.
```

그래서 대기 전환 점검이 이렇게 판정하고 있었다.

```js
if (rem >= t.pax) { ... }   // rem = 잔여 "객실 수", t.pax = "인원 수"
```

잔여 3실에 4명 팀이면 `3 >= 4` → **「✕ 잔여 부족」**. 트윈이면 2실이면 되는데 전환 가능한 팀을 놓치고 있었다. 1인 1실로 치는 셈이라 실제보다 두 배 보수적이다.

### 이름으로는 정원을 알 수 없다

현재 쓰이는 룸타입: 트윈 · 소형트윈 · 패밀리룸 · 별장 · 돔하우스 · 카라반. 숙소마다 표기가 달라 이름 규칙으로 정원을 유도할 수 없다. 포틴힐즈는 마스터에 `트윈 13 / 패밀리룸 19`인데, 이게 실제로 "2인실 / 4인실"인지도 이름만으로는 확정할 수 없다. **정원은 숙소별로 직접 입력받아야 한다.**

## 2. 1단계 — 구현한 것

### 데이터

리조트 객체에 `roomMeta`를 추가했다. `rooms`(객실 수)는 그대로 둔다.

```js
{
  rooms:    { '트윈': 13, '패밀리룸': 19, '싱글': 3 },
  roomMeta: {
    '트윈':     { pax: 2, online: true  },
    '패밀리룸': { pax: 4, online: true  },
    '싱글':     { pax: 1, online: false }   // 온라인 판매 제외
  }
}
```

- `pax` — 1방 정원(명). 인원을 객실 수로 환산하는 유일한 근거.
- `online` — 홈페이지 예약에 노출할지. **현재 대시보드 동작에는 영향이 없다.** 2단계 대비 데이터.

기존 저장본에는 이 필드가 없으므로 `normRoomMeta()`가 로드·불러오기·초기화 경로에서 채운다. 흔한 이름(트윈 2 · 패밀리룸 4 · 싱글 1 · "N인실" N)만 추정하고, 나머지는 **비워 두고 관리자가 입력**한다. 추정으로 조용히 채우면 틀린 값이 그대로 계산에 들어가기 때문이다.

정원이 비어 있는 룸타입이 있으면 마스터 카드에 경고를 띄운다.

### 순수 로직 (`shared/util.js` · 테스트 9케이스)

| 함수 | 하는 일 |
|---|---|
| `roomsNeeded(pax, per)` | 인원 → 필요 객실 수 (`ceil`) |
| `emptyBeds(pax, per)` | 그 배정에서 비는 자리 수 (요금 산정용) |
| `roomPlans(pax, types, opts)` | 인원을 채우는 **모든 조합**. 기본은 빈자리 0인 조합만 |
| `paxBookable(pax, types)` | 그 인원을 온라인에서 받을 수 있는가 |
| `bookablePax(types, max)` | 온라인에서 고를 수 있는 인원 목록 |

`roomPlans`는 방 개수 적은 순 → 빈자리 적은 순 → 큰 방 먼저로 정렬한다.

```
2인실·4인실이 있는 숙소
  2명 → 2인실×1
  4명 → 4인실×1 / 2인실×2
  8명 → 4인실×2 / 4인실×1+2인실×2 / 2인실×4
  3명·5명 → 조합 없음(빈자리 없이 못 채움)
2인실만 있는 숙소 → 짝수만
4인실만 있는 숙소 → 4의 배수만
```

### 대기 전환 점검 수정

```js
const per  = roomPaxOf(accom, room);      // 그 룸타입 정원
const need = MT.roomsNeeded(t.pax, per);  // 필요 객실 수
if (rem >= need) 전환 가능
```

표에 「잔여 3실 / 2실 필요」처럼 함께 보여준다. 정원이 등록되지 않은 룸타입은 **종전대로 1인 1실로 보수적으로** 계산하고 「△ 정원 미등록」으로 표시한다 — 조용히 낙관적으로 바꾸면 없는 방을 팔 수 있다.

## 3. 2단계 — 홈페이지 예약 연동 (제안)

### 확정된 규칙 (말씀하신 내용)

1. 2인실은 **정확히 2명**. 3인 이상은 4인실 쪽으로만.
2. 온라인에는 **싱글 타입을 올리지 않는다.** 트윈만 판매.
3. 회원권 인원만큼 방을 늘려 잡을 수 있다. 8인 회원권 → `2인실×4` 또는 `4인실×1+2인실×2` 등.
4. 싱글룸이 따로 없는 숙소(포틴힐즈)에서 1명이 자야 하면 **2인실에 1명 / 4인실에 2명 쓰는 비용**으로 산정한다.

1~3은 위 `roomPlans`가 그대로 표현한다. 인원 선택지는 `bookablePax(온라인 룸타입)`로 자동 생성되므로 숙소마다 다른 구성을 따로 코딩할 필요가 없다.

### 화면 흐름 제안

```
① 숙소·출발일 선택
② 인원 선택 — 온라인 판매 룸타입으로 채울 수 있는 수만 활성
     포틴힐즈(2·4인실) → 2, 4, 6, 8 …
     트윈만 있는 숙소   → 2, 4, 6 …
③ 방 구성 선택 (2가지 이상일 때만)
     8명 · 포틴힐즈
       ○ 4인실 2개
       ○ 4인실 1개 + 2인실 2개
       ○ 2인실 4개
④ 그날 잔여 확인 — blkPoolCapOn(풀, 날짜) 대비 조합별 객실 수
```

③은 요금이 달라지므로 조합마다 금액을 함께 보여줘야 한다.

### 잔여 확인은 룸타입별로 해야 한다

지금 `blkPoolCapOn(pool, ymd)`는 **풀 전체 합**을 돌려준다. "4인실 2개가 남았는가"는 답하지 못한다. 2단계에서는 룸타입 단위 조회가 필요하다.

```js
blkBlockOn(hotel, room, ymd)   // 이미 있다 — 그날 그 룸타입 보유
// 여기에 그날 그 룸타입 사용량을 빼는 함수가 추가로 필요
```

## 4. 확정된 판단

### 재고 단위는 객실이다 — 인원 케파로 바꾸지 않는다

호텔 계약이 방 단위이기 때문이다(야마나미 트윈 55실 / 소형트윈 50실). 인원으로 관리하면 3명 팀 10개가 인원 30을 차감하지만 실제로는 **20실**이 나가, 장부에 남았는데 방이 없는 상태가 된다. 엠클릭 원천 데이터도 방 단위다.

단, **임의배정형**(구마모토 시내 호텔, `assign:true`)처럼 호텔이 방을 미리 안 잡아주는 계약은 인원 관리가 맞고, 그 구조는 이미 있다. **계약 형태가 단위를 결정하며 혼합이 정답이다.**

"200명"이라는 감각은 영업 지표로는 유용하므로, 재고는 방으로 두되 화면에 인원 환산(잔여 3실 → 최대 6명)을 병기하는 것으로 충분하다.

### 빈자리 요금은 온라인에서 계산하지 않는다

사후 수기 정리로 처리한다. 따라서 온라인은 **인원 기준 기본 요금만** 산출하고, 2인실에 1명·4인실에 2명 같은 차액은 직원이 확정·정산 단계에서 정리한다.

이 판단의 결과로 **홀수 인원도 온라인에서 받을 수 있다.** 재고에서 방이 정확히 빠지기만 하면 되고(3명 → 2실), 요금 차액은 어차피 사람이 본다.

「3명이면 4명으로 예약하고 알려달라」는 방식은 권하지 않는다 — 4인 요금 결제 후 부분환불은 분쟁 소지가 있고, 실제 배정이 트윈 2실인지 4인실 1실인지 불명확하며, "알려달라"가 누락되면 4명분으로 방이 잡혀 오히려 블록을 더 쓴다.

### 온라인 예약은 「대기」로 접수한다

견적 → 대기 → 확정 → 정산 상태가 이미 있다. 온라인 예약을 대기로 넣으면 홀수 수용·빈자리 수기 정리·즉시 확정 결제 회피가 한 번에 풀린다. 골프 투어는 항공·그린피가 얽혀 즉시 확정이 어차피 어렵다.

```
손님: 인원 선택(홀수 포함) → 대기 접수
        ↓  재고는 이 시점에 방 단위로 홀드
직원: 방 배정 확정 + 빈자리 요금 수기 정리 → 확정
```

## 4-2. 회원권 예약가능인원

### 구조 — 두 층이다

| 층 | 값 | 어디에 |
|---|---|---|
| 회원권구분별 **기본** 인원 | 특별 2 · 골드 2 · 다이아1 4 · 다이아2 4 · EWRC1 4 · EWRC2 4 | 공통 마스터(구현됨) |
| 개인별 **실제 상한** | 「예약가능인원」 | 엠클릭 고객관리 + 별도 DB |

**개인별 값이 우선이다.** 실제 사례에서 회원권구분은 다이아몬드(기본 4인)인데 가족 회원권을 한 번호로 몰아 **예약가능인원 12명**으로 설정돼 있었다. 종류만 보고 판단하면 4명으로 잡아 8명을 거절한다.

### 구현한 것

공통 마스터에 「회원권 예약가능인원」 표를 넣었다(`commonMaster.memberPax`). 조회는 `memberPaxOf(회원권구분)`.

업로드된 데이터에 있는데 표에 없는 회원권구분은 경고로 띄우고 한 번에 추가할 수 있게 했다 — **엠클릭 표기와 표의 이름이 글자 단위로 같아야** 조회되므로, 표기 불일치를 스스로 잡게 하려는 장치다.

### 남은 연결 — 개인별 예약가능인원

두 식별자의 성격이 확인됐다.

| | 무엇 | 쓰임 |
|---|---|---|
| **회원번호** (`LEE01035295206`) | 회원이 홈페이지에서 예약할 때 쓰는 아이디 | **온라인 예약의 결합 키** |
| **고객번호** (`146260`) | 백오피스에 등록할 때 생성되는 내부 순번 | 사내 조회용 |

그래서 **홈페이지 예약에서는 결합 문제가 없다** — 회원이 로그인한 상태이므로 회원번호로 예약가능인원을 바로 조회하면 된다.

결합이 필요한 곳은 **대시보드**뿐이다. 업로드한 예약 데이터에 개인별 상한을 붙여 검증하려면 예약리스트에 회원번호 컬럼이 있어야 하는데, 현재 파싱에는 `대표고객`(이름)과 `회원권구분`만 있다(원본 행은 `raw`에 보관되므로 컬럼만 있으면 파싱 추가는 간단하다). 이름만으로 붙이면 동명이인에서 틀린다.

우선순위가 낮다 — 온라인 예약 쪽이 먼저 필요해지면 그때 붙이면 된다.

## 4-4. 블록 표와 마스터의 관계 (자주 오해하는 지점)

**블록 현황 표의 행은 마스터가 아니라 붙여넣은 엠클릭 표에서 나온다.** 그것도 사용 수가 1 이상인 칸만 행이 된다(`blkParse`).

| | 출처 |
|---|---|
| 어떤 숙소·룸타입 행이 보이는가 | 엠클릭 표 (실제 사용) |
| 그 행의 보유·잔여 | 리조트 마스터 |

그래서 마스터에서 룸타입을 지워도 **엠클릭에 예약이 잡혀 있으면 행은 남고 「보유미등록」이 된다.** 이건 동기화 실패가 아니라 실제 불일치를 드러내는 것이다. 예약이 들어와 있는 방을 화면에서 숨기면 실제로 나가는 객실이 안 보이게 되므로 숨기지 않는다.

대신 「마스터와 맞지 않는 항목」 카드에서 그 자리에서 해소할 수 있게 했다.

- **숙소가 마스터에 없음** — 숙소 등록 또는 숙소명 별칭
- **룸타입이 마스터에 없음** — ① 마스터에 추가(보유 수 입력) ② 기존 룸타입에 별칭 연결

예: 「소형트윈」을 없애고 트윈으로 합쳤다면 별칭 연결이 맞다. 정말 없어진 룸타입이면 마스터에 추가할 필요 없이, 그 달 예약이 소진되면 표에서도 사라진다.
