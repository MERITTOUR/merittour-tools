# 룸타입 정원과 온라인 예약 인원 규칙

> 1단계(정원 데이터 + 대기 전환 환산): **구현 완료**
> 2단계(홈페이지 예약 연동): **설계 제안 — 확인 필요**
>
> 순수 로직은 `shared/util.js`, 마스터 UI는 `tools/dashboard/index.html`

---

## 1. 출발점 — "인원 = 객실 수"가 아니다

골프투어는 2인 1실이 기본이다. 그런데 마스터에는 **객실 수만** 있고 정원(1방에 몇 명)이 없었다.

```js
rooms: { '트윈': 15 }      // 15실이라는 것만 안다. 몇 명이 자는 방인지는 모른다.
```

그래서 대기 전환 점검이 이렇게 판정하고 있었다.

```js
if (rem >= t.pax) { ... }   // rem = 잔여 "객실 수", t.pax = "인원 수"
```

잔여 3실에 4명 팀이면 `3 >= 4` → **「✕ 잔여 부족」**. 트윈이면 2실이면 되는데 전환 가능한 팀을 놓치고 있었다. 1인 1실로 치는 셈이라 실제보다 두 배 보수적이다.

### 이름으로는 정원을 알 수 없다

현재 쓰이는 룸타입: 트윈 · 소형트윈 · 패밀리룸 · 별장 · 돔하우스 · 카라반. 숙소마다 표기가 달라 이름 규칙으로 정원을 유도할 수 없다. 포틴힐즈는 마스터에 `트윈 13 / 패밀리룸 19`인데, 이게 실제로 "2인실 / 4인실"인지도 이름만으로는 확정할 수 없다. **정원은 숙소별로 직접 입력받아야 한다.**

## 2. 1단계 — 구현한 것

### 데이터

리조트 객체에 `roomMeta`를 추가했다. `rooms`(객실 수)는 그대로 둔다.

```js
{
  rooms:    { '트윈': 13, '패밀리룸': 19, '싱글': 3 },
  roomMeta: {
    '트윈':     { pax: 2, online: true  },
    '패밀리룸': { pax: 4, online: true  },
    '싱글':     { pax: 1, online: false }   // 온라인 판매 제외
  }
}
```

- `pax` — 1방 정원(명). 인원을 객실 수로 환산하는 유일한 근거.
- `online` — 홈페이지 예약에 노출할지. **현재 대시보드 동작에는 영향이 없다.** 2단계 대비 데이터.

기존 저장본에는 이 필드가 없으므로 `normRoomMeta()`가 로드·불러오기·초기화 경로에서 채운다. 흔한 이름(트윈 2 · 패밀리룸 4 · 싱글 1 · "N인실" N)만 추정하고, 나머지는 **비워 두고 관리자가 입력**한다. 추정으로 조용히 채우면 틀린 값이 그대로 계산에 들어가기 때문이다.

정원이 비어 있는 룸타입이 있으면 마스터 카드에 경고를 띄운다.

### 순수 로직 (`shared/util.js` · 테스트 9케이스)

| 함수 | 하는 일 |
|---|---|
| `roomsNeeded(pax, per)` | 인원 → 필요 객실 수 (`ceil`) |
| `emptyBeds(pax, per)` | 그 배정에서 비는 자리 수 (요금 산정용) |
| `roomPlans(pax, types, opts)` | 인원을 채우는 **모든 조합**. 기본은 빈자리 0인 조합만 |
| `paxBookable(pax, types)` | 그 인원을 온라인에서 받을 수 있는가 |
| `bookablePax(types, max)` | 온라인에서 고를 수 있는 인원 목록 |

`roomPlans`는 방 개수 적은 순 → 빈자리 적은 순 → 큰 방 먼저로 정렬한다.

```
2인실·4인실이 있는 숙소
  2명 → 2인실×1
  4명 → 4인실×1 / 2인실×2
  8명 → 4인실×2 / 4인실×1+2인실×2 / 2인실×4
  3명·5명 → 조합 없음(빈자리 없이 못 채움)
2인실만 있는 숙소 → 짝수만
4인실만 있는 숙소 → 4의 배수만
```

### 대기 전환 점검 수정

```js
const per  = roomPaxOf(accom, room);      // 그 룸타입 정원
const need = MT.roomsNeeded(t.pax, per);  // 필요 객실 수
if (rem >= need) 전환 가능
```

표에 「잔여 3실 / 2실 필요」처럼 함께 보여준다. 정원이 등록되지 않은 룸타입은 **종전대로 1인 1실로 보수적으로** 계산하고 「△ 정원 미등록」으로 표시한다 — 조용히 낙관적으로 바꾸면 없는 방을 팔 수 있다.

## 3. 2단계 — 홈페이지 예약 연동 (제안)

### 확정된 규칙 (말씀하신 내용)

1. 2인실은 **정확히 2명**. 3인 이상은 4인실 쪽으로만.
2. 온라인에는 **싱글 타입을 올리지 않는다.** 트윈만 판매.
3. 회원권 인원만큼 방을 늘려 잡을 수 있다. 8인 회원권 → `2인실×4` 또는 `4인실×1+2인실×2` 등.
4. 싱글룸이 따로 없는 숙소(포틴힐즈)에서 1명이 자야 하면 **2인실에 1명 / 4인실에 2명 쓰는 비용**으로 산정한다.

1~3은 위 `roomPlans`가 그대로 표현한다. 인원 선택지는 `bookablePax(온라인 룸타입)`로 자동 생성되므로 숙소마다 다른 구성을 따로 코딩할 필요가 없다.

### 화면 흐름 제안

```
① 숙소·출발일 선택
② 인원 선택 — 온라인 판매 룸타입으로 채울 수 있는 수만 활성
     포틴힐즈(2·4인실) → 2, 4, 6, 8 …
     트윈만 있는 숙소   → 2, 4, 6 …
③ 방 구성 선택 (2가지 이상일 때만)
     8명 · 포틴힐즈
       ○ 4인실 2개
       ○ 4인실 1개 + 2인실 2개
       ○ 2인실 4개
④ 그날 잔여 확인 — blkPoolCapOn(풀, 날짜) 대비 조합별 객실 수
```

③은 요금이 달라지므로 조합마다 금액을 함께 보여줘야 한다.

### 잔여 확인은 룸타입별로 해야 한다

지금 `blkPoolCapOn(pool, ymd)`는 **풀 전체 합**을 돌려준다. "4인실 2개가 남았는가"는 답하지 못한다. 2단계에서는 룸타입 단위 조회가 필요하다.

```js
blkBlockOn(hotel, room, ymd)   // 이미 있다 — 그날 그 룸타입 보유
// 여기에 그날 그 룸타입 사용량을 빼는 함수가 추가로 필요
```

## 4. 확인이 필요한 것

### ① 홀수 인원을 온라인에서 받는가

"2명 또는 4명만 선택"과 "3인 이상은 4인실 쪽"이 함께 있어 두 갈래로 읽힌다.

- **A안(현재 구현)** — 딱 떨어지는 인원만. 3·5·7명은 온라인 불가, 전화 문의로 안내.
- **B안** — 홀수도 받되 빈자리를 요금에 반영. 3명 → 4인실 1개(1자리 빔) 또는 2인실 2개(1자리 빔).

`roomPlans(pax, types, {exact:false})`가 이미 B안을 지원한다. 빈자리 수(`empty`)도 함께 돌려주므로 요금 계산에 바로 쓸 수 있다.

### ② 빈자리 요금을 어떻게 매기는가

"2인실에 1명, 4인실에 2명 쓰는 비용"이 구체적으로 무엇인지 정해야 한다.

- 방값 전체를 실제 인원이 나눠 부담 (= 1명이 2인분 체재비)
- 아니면 1인 체재비 + 정액 싱글차지
- 4인실에 2명이면 4인분인가, 2인분 + 추가금인가

현재 정산은 **1인 체재비 × 인원**으로만 계산한다. 빈자리 개념이 없어서 지금 구조로는 표현되지 않는다.

### ③ 회원권 인원은 어디서 오는가

엠클릭에 `회원권구분`이 있지만 **문자열 라벨**이고 "몇 명까지"인지는 없다. 8인 회원권을 시스템이 알려면 `회원권구분 → 인원` 매핑 테이블이 마스터에 필요하다. 종류가 몇 가지이고 각각 몇 명인지 알려주시면 추가하겠다.
